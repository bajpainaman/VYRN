# Vx friction log

Every Vx workaround and every Vx feature we looked for and did not find, each naming its
vx-lang/Vx issue (spec/11-build.md §5.6). Code sites carry `// VX-WORKAROUND W-nn (...)` or
`# VX-WORKAROUND W-nn (...)`. All entries below were found with vxc v0.0.4 (c6dffec7) on x86_64
Linux while writing `vyrn-vx-oracle` (W-09 to W-15) and `vyrn-vx-client` (W-01, W-03, W-05,
W-17 to W-20). Their upstream issues are not filed yet: §5.5 needs a
maintainer-facing minimal reproduction and a CLA-signed author, so each is `open, issue to file`.

| W-10 | A vxc release binary for Linux, so `vx/TOOLCHAIN`'s `vxc_blake3` names one artifact. There is none for v0.0.4, so the pin is the hash of a local build. The first pin (`855e5244…`) did not reproduce: a second x86_64 build hashed `c129e3e8…`, because one embedded the toolchain path `.rustup/toolchains/1.100.0-x86_64-unknown-linux-gnu` and the other `stable`, and both embedded absolute `~/.cargo/registry` paths. `.agents/setup` now builds vxc with `RUSTUP_TOOLCHAIN` = the rust-toolchain.toml pin and remaps three prefixes: `$CARGO_HOME/registry/src`, the toolchain sysroot, and (last, since the last match wins) the sysroot's rust-src, back to `/rustc/<commit>`. Without the third rule, a toolchain with rust-src embeds sysroot paths where one without it embeds `/rustc/<commit>`. Two clean x86_64 builds in `~/.local/src/vx/target`, one on toolchain `stable` and one on `1.100.0` (the same rustc 0ef1bc386), both hashed `da38286d…`. That pin did not reproduce on a second orb (`a12dedc6…`, also stable across its own clean builds) with the same packages, CPU flags, paths and `.rs`/`.inc`/`.o` outputs: mlir-sys 220.0.2's build script links every `libMLIR*.a` of LLVM's libdir in `read_dir` order, and tblgen 0.9.1's archives `cc/lib` in that order, and directory order differs between filesystems, so the static link order (and vxc's code layout, +5 KiB `.text`) differed. `.agents/setup` now patches both build scripts to sort by name; sorted clean builds on both orbs hash `02fddd17…`, the pin. Still host-specific: vxc embeds its source dir (`~/.local/src/vx`, read at run time for its stdlib) and its target dir (tablegen `.inc` paths from build.rs, which `RUSTFLAGS` does not reach), so the pin holds for `HOME=/home/user` and setup's layout. At run time vxc also reads `~/.local/src/vx/stdlib/` and loads `target/release/libvx_std_core.so` and its build-script `out/`'s `libvx_mlir_shims.so` and `libvx_x86_dispatch.so`, so a vxc binary copied alone fails `--audit` (found when CI cached only the binary). | `vx/TOOLCHAIN` pins one hash per host kind (`vxc_blake3.x86_64-linux`); `vx/build.sh` refuses a mismatch and skips a host with no pin unless `VYRN_REQUIRE_VX=1`. A pin is added only once clean builds on two machines of that host kind match. `.agents/setup` sorts mlir-sys's and tblgen's directory listings (`vxc_sort_build_scripts`). CI's `vx` job caches the binary with exactly those files (they build byte-identical libraries). | `vx/TOOLCHAIN`, `vx/build.sh`, `.agents/setup`, `.github/workflows/ci.yml` | aarch64 and macOS hosts skip the Vx tests until a build on them is pinned; a host with another `HOME` gets another hash | a release artifact per target, or vxc locating its stdlib without an embedded absolute path (and mlir-sys/tblgen sorting upstream) | open, issue to file |
